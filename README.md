# shuiyinya-config-pages

水印鸭的远程配置。`version.json` 由 GitHub Pages 提供，客户端从
`https://analytics.milodev.cn/config/version.json` 拉取。

> ⚠️ 改这里等于改线上，没有灰度。改完必须在真机上验证客户端**确实用上了** ——
> 「发出去」不等于「被采纳」（公告就因为客户端的 14 天上限被 fail-closed 判死过一次）。

---

## `platformPolicies` · 抖音走 `cloud_first` 是**正式架构**，不是临时开关

```json
"platformPolicies": { "douyin": { "route": "cloud_first" } }
```

**这条不要「改回 `{}`」。** 2026-08-11 它确实是作为权宜之计下的，当时的注释写着
「209 发版后改回 `{}`」—— **那句话已作废**，2026-08-30 站长裁定转正。

### 为什么转正

1. **当初的前提被推翻了。** 下这个开关是为了绕开「抖音夜间设门禁」，
   后来查实夜间熄火的主因是**我们自己的机器被压垮**，不是平台门禁。
   于是「让客户端自己感知门禁」那套设计要解决的问题并不存在。

2. **服务端这条路在能力上严格更强，而且搬不过去。** 抖音签名接口依赖
   `a_bogus`，而客户端的原生桥**显式剥掉 `Cookie`**
   （`MainActivity.java` 的 `isSensitiveHeader`），签名配方整个立在 cookie 上。
   ⇒ 能让它变成客户端可做的那个改动，自己必须发版才能落地。
   客户端只能走分享页，不签名，天花板更低。

3. **数据支持。** 2026-08-31 实测 v300 抖音成功率 **97.8%**（354 成 / 8 败，129 人），
   是历史最好的一档。

### 什么情况下重新考虑

- 解析服务器再次因抖音流量出现容量问题（当初压垮机器的是浏览器路，
  签名路开销小得多，但这不是永久保证）
- 抖音签名方案失效且短期无解，而客户端分享页那条反而还活着

## 读汇总成功率的注意事项（2026-08-30 起）

停服墙上线后，**旧版的解析尝试会记成 `parse_fail`**，把汇总数字拖得很难看：

| 日期 | 汇总 | v300 | v207 |
|---|---|---|---|
| 08-29（墙前） | 97% | 97.7% | 97.3% |
| 08-30 | 70% | **98.7%** | 23.3% |
| 08-31 | 63% | **97.8%** | **0%** |

⇒ **汇总数已经不能代表健康度**，必须按 `version_code` 拆开看。
告警侧已经带版本切片（`parseHealthAlert.ts` 的 `loadVersionSlices`），
看板卡片还没有。
